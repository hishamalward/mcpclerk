The story, in one paragraph

An agent on MCP can call any tool its servers expose, as often as it likes, with any arguments, and nothing records it in a form anyone can audit. The enterprise question is not whether the agent can do the job; it is what is it allowed to do, who approved the dangerous parts, and what did it actually do. mcpclerk is a small MCP server that sits between the agent and the real servers and answers those three with code: a per-tool allowlist (deny by default), a hold-for-a-human step on write-class tools, per-tool quotas, redaction of secret-looking arguments before anything is logged or shown, and an append-only, hash-chained audit log with a verify command. It deliberately does not do identity, a UI, remote approval channels, or anything that needs an upstream patched. From the demo log in examples/audit.demo.jsonl: 10 entries, 7 calls, 1 approved, 2 refused (one by policy, one by quota), chain intact.

The code, in call order

cli.py · _serve(). Loads the policy, opens the log, opens /dev/tty if there is one, builds the Proxy and runs the low-level server over stdio_server(). Why: the proxy uses the SDK's low-level Server with on_list_tools / on_call_tool callbacks rather than the decorator API, because a proxy does not know its tools at import time; it discovers them.
policy.py · load_policy(), Policy.resolve(). Parses YAML, validates every key, expands ${VAR} from the environment, records the file's SHA-256 so a log can be tied to the policy that produced it. resolve returns the rule for a tool: exact name, then the longest matching glob, then defaults.unlisted. Why: deny by default, because an unlisted tool is an unreviewed tool, and the cost of the default being wrong is asymmetric.
server.py · Proxy.start(). Opens each upstream, lists its tools, builds the exposed set. Tools whose decision is deny are left out of tools/list; a discover event records exposed and hidden counts. Why: hide rather than list-and-refuse: an agent cannot be tempted by a tool it cannot see, and a hidden tool called by name is still refused and logged, so hiding costs nothing in enforcement.
server.py · Proxy.call_tool(). The pipeline, top to bottom, in the order the diagram shows. Quota is checked before approval so a human is never asked to bless a call that would be refused anyway. Every branch ends in self.log.append(entry). Why: quota is consumed by every attempt that gets past the check, including one a human later refuses, because it was a real attempt on the upstream's budget; refused-by-quota calls are not counted, so a stuck agent does not push its own window out.
redact.py · Redactor.redact(). Returns a redacted deep copy: key rules replace whole values, value rules replace matches, and the replacement names the rule ([REDACTED:kv-secret]). Pure; no I/O. Why: redact for the log, not for the upstream, because the proxy must never change what the tool does. test_upstream_receives_unredacted_args sends a fake API key through a secret_sink tool that echoes its input and asserts the upstream saw it and the log did not.
approval.py · request_approval(), approve_loop(). Writes approvals/<id>.json with the redacted arguments and polls it every 250 ms, racing a terminal prompt if a terminal exists, until an answer or the timeout. approve_loop is the same prompt running in a second terminal (mcpclerk approve). Why: the file queue is the mechanism and the terminal is a client of it. The MCP SDK starts stdio servers with start_new_session=True, so a proxy launched by an agent has no terminal; this was found during the build when the recorded demo's y never arrived. Timeout is a refusal because silence on a write means no.
quota.py · QuotaBook.try_acquire(). A per-run counter and a 60-second sliding window per tool, clock injected so tests do not sleep. Returns None and counts, or a refusal with the seconds until the window frees. Why: the refusal text carries the number the agent needs (retry after 41s) so a well-behaved agent can wait instead of guessing.
upstream.py · Upstream.open(), call(). One SDK Client per upstream for the life of the run; stdio_client(params) already satisfies the SDK's Transport protocol, so stdio and HTTP upstreams differ only in construction. Tests inject an in-memory server instead. Why: fail loudly if the policy sets HTTP headers the SDK cannot send, rather than silently send none; a control that silently degrades is worse than no control.
audit.py · AuditLog.append(), verify(), report(). Each entry gets seq, prev_hash and hash = sha256(prev_hash + "\n" + canonical(entry)); the file is opened O_APPEND and fsynced per entry; the chain continues across runs in the same file. verify recomputes everything and checks that run-end claims the number of entries the run actually has. Why: a hash chain rather than signatures, because the threat is quiet editing by someone with write access, not forgery by an outsider; a chain makes every edit visible and costs nothing to run. Results are not stored, only their size and types, so the log cannot become a second place secrets leak.

How to read the log

One JSON object per line. kind is event (run-start with the policy's SHA-256 and the flags, discover with exposed and hidden counts, run-end with the entry count) or call. On a call, decision is one of allowed, approved, refused-denied, refused-unknown, refused-quota, refused-timeout, refused-by-human; approved_by is terminal, file or session-flag. latency_ms is upstream time only; the human's thinking time is held_ms, so p95 in report means the tool, not the person. args is the redacted copy; results are never stored, only content_bytes and content_types. seq, prev_hash and hash are the chain: mcpclerk verify recomputes every hash and names the first line that does not match. A run-start with approve_session: true means every approval in that run was automatic; report prints a warning for it.

Interview answers

Why a proxy and not hooks inside the agent?

Hooks live in the agent's process and are only as trustworthy as the agent's configuration, which the agent can often edit. A proxy is a separate process with its own policy file and its own log, and it works for any MCP client, not one vendor's hook API. The price is one more process and a namespaced tool name.

How is this different from the gateways that already exist?

Lasso's mcp-gateway, IBM's context-forge and Docker's MCP Gateway are platforms: registries, auth, plugins, observability. mcpclerk is about 1,000 lines with one dependency beyond the SDK, five controls, and a log you can verify with one command. It claims smallness and verifiability, not novelty.

What happens when approval times out, and why is that a refusal?

The call is not forwarded, the agent receives refused-timeout as a readable error, and the log records it with held_ms equal to the timeout. The proxy cannot tell "no" from "not yet", and the safe reading of silence on a write is no; the agent can ask again and a human can answer.

How would you extend this to per-user identity?

Put an identity on the request (a header on HTTP transport, or an authenticated client session), key the policy by principal as well as tool, and record approved_by as a real identity rather than a channel. The pipeline does not change; the policy resolver and the approval record gain one dimension.

What would an attacker do first, and what does this not stop?

Call a hidden tool by name: refused and logged. Then look for an allow that is too broad, or a secret the redactor does not recognise: the policy is your judgement, and the pattern list is finite. With write access to the log file, rewrite the whole chain from genesis: the chain is not a signature. An external anchor for the daily head hash is the next step.

How does this relate to the framework and to ToilScan?

Same instinct at three layers. ToilScan bounds blast radius on a developer tool's writes (preview by default, explicit apply, a journal). agentkeel bounds it on an agent's code changes (spec first, gates, hooks). mcpclerk bounds it on an agent's tool calls: allowed, approved, recorded.

Check yourself

1. A tool is approve in the policy and the human never answers. What does the agent see, and what is in the log?

An error result with is_error: true and the text mcpclerk: refused-timeout fs.write_file: no approval within 120s. One log entry with decision: refused-timeout, outcome: not-forwarded, and held_ms equal to the timeout.

2. The policy allows read_* and denies read_media_file. Which wins?

The exact name. Resolution is exact, then longest glob, then default; read_media_file is denied and is not listed to the agent.

3. Why does the upstream receive a password that the log shows as [REDACTED:kv-secret]?

Because redaction is applied to a copy used for the log and the approval prompt only. Changing what the upstream receives would change what the tool does, and a proxy that changes tool behaviour is no longer a proxy. The test that proves it sends a secret through a tool that echoes its input.

4. Someone edits one character in line 4 of the log. What does verify print, and what if they delete line 4 instead?

FAIL at line 4: hash does not match entry content (edited). If deleted: FAIL at line 4: seq 5 but expected 4 (missing or reordered entry). If they delete the last call of a finished run, run-end's count no longer matches and verify reports truncation.

5. Why does mcpclerk approve exist when the proxy already prompts on the terminal?

Because the proxy usually has no terminal. MCP clients spawn stdio servers in a new session, so /dev/tty cannot be opened. The file queue is the real mechanism; the in-process prompt only works when a human starts the proxy by hand, and mcpclerk approve is the same prompt running in a terminal that exists.
